# 场景协作开发规范 · 平民宇宙

> 协作理念：平民宇宙是「内容驱动」架构——引擎只认「数据」，不认「谁写的」。
> 每位成员可以**完全自由**地设计一座城市或乡村场景：风格、题材、叙事、氛围自定，
> 唯一约束是：**产出符合统一 schema 的数据模块 + 遵守下面的整合规范**。
> 这样既能百花齐放，又能被引擎自动整合、统一发布。

---

## 一、每位成员需要提交什么

### 1. 核心交付：一个「场景数据模块」（必交）

你实现的场景 = 一个纯 JS 数据文件，**不要去改引擎代码**。
项目已采用**分包目录**：每个场景一个独立文件，互不冲突。

- **文件位置**：`src/content/scenes/<场景id>.js`
- **写法（按 registry 注册，不是 export default）**：
  ```js
  // src/content/scenes/my_lighthouse.js
  // 纯数据模块：只描述场景，引擎据此生成 3D 与玩法。字段见 schema.md
  import { SCENE_REGISTRY } from './registry.js';

  SCENE_REGISTRY.push({
    id: 'my_lighthouse',
    name: '海边灯塔',
    sky: '#9ec9e0',
    ground: '#d9c7a3',
    fog: 0.012,
    spawn: [0, 0, 6],
    props: [ /* box/cyl/cone/sphere，纯几何+颜色 */ ],
    spots: [ /* 发光互动点 + 事件 */ ],
  });
  ```
- 字段与约束见 `src/content/schema.md`（权威）。
- 写完后跑 `npm run sync`，聚合脚本会自动把它纳入游戏；无需手改任何聚合文件。

### 2. 美术 / 概念素材（可选）

引擎支持把 AI / ComfyUI 生成的概念图**直接贴到场景**——现已落地 `texture` / `groundTex` 字段：

- 道具级：`prop.texture = 'assets/scenes/<id>/sofa.png'`，贴到该道具表面（文件缺失时自动降级为纯色，不报错）。
- 场景级：`groundTex = 'assets/scenes/<id>/floor.png'`，贴到地台（缺失时降级为 `ground` 纯色）。
- 把贴图放进 `assets/scenes/<场景id>/`；
- 在场景对象的 `meta` 字段登记：`meta: { author: '你的昵称', style: '赛博/古风/治愈…', art: 'assets/scenes/my_lighthouse/concept.png', note: '灵感来源…' }`；
- 字段定义见 `src/content/schema.md`。提交贴图后，合并即可在游戏中看到你的美术。

### 3. 叙事扩展（可选，需评审）

如果你想加「专属身份」或「专属年度行动」（会轻微影响全局数值平衡），单独提 PR 到：

- `src/content/identities.js`（身份）
- `src/content/actions.js`（年度行动）

这类改动需维护者评审，避免破坏经济/数值平衡。

### 4. 自述信息（必交）

在 PR 描述里写明（或在文件头注释）：**作者昵称、场景风格、灵感来源、是否用到 AI 生图**。
这是「平民共创」的署名与溯源依据。

## 二、统一整合与兼容规范

### 1. ID 全局唯一 + 命名约定

- `scene.id` 必须全局唯一，建议前缀防撞车：`my_lighthouse`、`zl_oldtown`、`ai_neonbay`。
- 互动点 `spot.id` 在**同一场景内**唯一即可。
- ID 只用小写字母、数字、下划线，不用中文（避免 URL/路径问题）。

### 2. 坐标空间约定

- 每个场景是独立小世界，玩家在场景内自由走动。
- **地台**由作者第一个 `box` 道具（地面）定义，建议宽/深 ≥ 14，保证走动空间。
- 所有 `props` / `spots` 的 `pos` 必须落在该地台范围内（一般 `|x|、|z| ≤ 8`，避开边缘以免「走出世界」）。
- 高度 `y`：地面在 `y≈0`，叠放物向上为正。

### 3. 颜色 / 材质规范

- `sky / ground / color` 必须是十六进制 `#RRGGBB`。
- `emissive`（自发光）只用于灯、霓虹、屏幕等「会发光」的物体；避免大面积滥用导致过曝。

### 4. 属性键白名单 + 数值预算

- `event.choices[].effect` 只允许七键：`health / happy / energy / knowledge / social / reputation / money`。
- 单次选择数值建议 `≤ ±15`；`money` 可负（消费），但单场景总收支建议平衡，避免刷属性。
- 属性会被引擎钳制在 `0~100`，`money` 不限。

### 5. 道具类型白名单 + size 维度

| type | size 维度 | 用途 |
|------|-----------|------|
| `box` | `[宽,高,深]` | 建筑/家具 |
| `cyl` | `[半径,高]` | 树/柱/灯 |
| `cone` | `[半径,高]` | 屋顶/树冠 |
| `sphere` | `[半径]` | 灯/装饰 |
| `plane` | `[宽,深]` | 少用（地面已自动生成） |

可选字段：`emissive`、`rotY`（弧度）。

### 6. 性能预算（保证手机流畅）

- 单场景 `props ≤ 40`、`spots ≤ 6`。
- 同屏不要堆大量自发光体（手机 GPU 吃不消）。

### 7. 纯数据约束（铁律）

- 场景文件是**纯数据**：不能写函数、不能有 `eval`、不能直接 `import` 引擎、不能有副作用。
- 唯一允许的 import 是 `import { SCENE_REGISTRY } from './registry.js';`，随后 `SCENE_REGISTRY.push(场景对象)`。
- 引擎通过 `tools/sync-scenes.mjs` 扫描 `src/content/scenes/*.js` 自动生成 `index.js` 聚合，你只负责「写自己的文件」。

### 8. 分包目录机制（✅ 已落地，零冲突）

- 每个场景独立成 `src/content/scenes/<id>.js`，互不干扰；
- 任何人（含创始神）**只往目录加自己的文件、从不手改聚合器**，彻底消灭多人改同一文件的冲突；
- 聚合出口 `src/content/scenes/index.js` 由 `npm run sync` 自动生成（已在 `validate`/`build` 中自动调用）；
- 创始神生成的场景也写入该目录（分支 `god/map-*`），与人工 PR 平权。

### 9. 自动校验

提交前必跑（任选其一）：
- `npm run sync` —— 重新聚合场景目录；
- `npm run god --check` 或 `node tools/creator-god/generate.mjs --check` —— 校验所有场景是否符合 schema；
- `npm run validate` —— 一键执行「sync + schema 校验 + 全模块打包编译」，合并前 CI 也跑它。

## 三、合并与正式发布流程

### 1. 分支策略

```bash
git checkout main
git pull origin main
git checkout -b feat/scene-<你的场景id>   # 例：feat/scene-my-lighthouse
# 只改你自己的 src/content/scenes/<id>.js（+ 可选 assets）
npm run sync                              # 顺手更新 index.js（也可留到 PR 时由 CI 生成）
git add src/content/scenes/<id>.js
git commit -m "feat(scene): 新增 <场景名> by <作者>"
git push -u origin feat/scene-<你的场景id>
```

### 2. PR 内容

PR 标题/描述写明：**场景名 · 作者 · 风格 · 自测结果**（`npm run dev` 截图或文字描述「无控制台报错、能正常走动与互动」）。

### 3. 自动校验卡

PR 会触发 `npm run validate`：schema 完整 + 全模块编译通过。不通过将自动标记，无法合并。

### 4. 人工评审清单（维护者）

- [ ] `scene.id` 全局唯一、命名合规
- [ ] 坐标落在地台内、未「走出世界」
- [ ] `props ≤ 40`、`spots ≤ 6`
- [ ] `effect` 只用七键、数值在预算内
- [ ] 纯数据、无引擎改动、无副作用
- [ ] 自述信息完整（作者/风格/灵感）

### 5. 里程碑式发布（合并即正式）

- 采用**里程碑发布**：每积累一批场景（或每月）打一个版本 tag（如 `v2.1`、`v2.2`）。
- 评审通过的 PR 合并进 `main` 即为「纳入正式版本」，玩家刷新即见。
- 发版时跑 `npm run validate`（内含 `build`）产出单文件 `dist/平民宇宙.html` 作为可分发正式版，并更新 README 的场景列表。

### 6. 创始神与人工 PR 平权

- 创始神每小时自动长的地图走同样的流程（分支 `god/map-<时间戳>`），与人工 PR **平权**。
- 创始神只负责「提 PR」，不自动合并；质量仍由维护者/社区评审把关（已配置本机 GitHub token 全自动建 PR）。

### 7. 冲突处理

- 因每人独立文件，**基本无冲突**。
- 聚合文件 `index.js` 由脚本生成、不在 PR 手动维护，彻底消除旧式"大数组"冲突。
- 若两人改到同一全局文件（如 `identities.js`），由维护者协调合并顺序。

### 8. 发版清单（checklist）

1. 所有待发场景 PR 已合并 `main`
2. `npm run validate` 全绿（`sync` + schema + 打包）
3. `dist/平民宇宙.html` 产出并本地实测渲染
4. README 场景列表更新
5. 打 tag `vX.Y` + GitHub Release 说明本次新增场景与作者
